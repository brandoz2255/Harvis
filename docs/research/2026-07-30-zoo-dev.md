# Zoo (zoo.dev) — Text-to-CAD / KCL / Design Studio — deep research + integration plan

Date: 2026-07-30. Researched from primary sources only: the live OpenAPI spec fetched from
`https://api.zoo.dev/` (1.18 MB, `Zoo API v0.1.0`), the live pricing API
(`GET https://api.zoo.dev/pricing/subscriptions`), zoo.dev product/docs pages, the
`kittycad` GitHub org (repo list pulled from the GitHub API), and repo READMEs.
Anything I could not verify is marked UNVERIFIED. Target project: **forge-fab-assistant**
(Adaptive Space). Locked decision respected throughout: **build123d stays the local kernel;
Zoo is a wrap-only cloud side adapter.**

---

## 1. What it actually is

Zoo (formerly KittyCAD; GitHub org still `kittycad`) is a cloud CAD company built around
three things:

1. **A proprietary GPU geometry engine** (Vulkan-based, cloud-hosted). It is the only part
   that does actual geometry. Their own README: *"The 3D view in Design Studio is just a
   video stream from our hosted geometry engine. The app sends new modeling commands to the
   engine via WebSockets, which returns back video frames."*
   (source: https://github.com/KittyCAD/modeling-app README)
2. **KCL (KittyCAD Language)** — a code-first parametric CAD DSL. Every GUI click in Design
   Studio generates KCL under the hood; the KCL file IS the model.
   (source: https://zoo.dev/docs/kcl-book/intro.html)
3. **ML endpoints (Text-to-CAD / Zookeeper)** — models that emit KCL + geometry from
   prompts. Zookeeper is their conversational CAD agent in Design Studio / app.zoo.dev;
   its API-side equivalents are the ML endpoint family and the `/ws/ml/copilot` websocket.
   (sources: https://zoo.dev/zookeeper, https://zoo.dev/research/zookeeper, OpenAPI spec)

**Open vs proprietary (verified from the org's repo list + licenses):**

| Open (license) | Proprietary / cloud-only |
|---|---|
| `modeling-app` — Zoo Design Studio, incl. `rust/kcl-lib` (KCL parser, interpreter front-end, LSP, WASM) — MIT, 1,267★ | **The geometry engine** — no public repo, cloud-hosted, GPU |
| SDKs: `kittycad.py`, `.rs`, `.ts`, `.go` — MIT | The ML / Text-to-CAD / Zookeeper models |
| `cli` (MIT), `mcp` — an official Zoo MCP server (MIT) | app.zoo.dev hosted service |
| `modeling-api` types (MIT), `ezpz` constraint solver (MIT), `tree-sitter-kcl`, `kcl-book` (MIT) | |

Decisive nuance: **KCL's toolchain is open, but KCL cannot produce geometry locally.**
`kcl-lib` parses/lints/completes locally (it's the WASM LSP inside Design Studio), but the
standard-library geometry operations execute as engine commands over `/ws/modeling/commands`
against api.zoo.dev — the kcl-lib README literally requires "a production Zoo dev token" to
run its own stdlib tests. There is **no self-hosted or on-prem engine option anywhere** in
the docs, ToS, or repos.

**Prior-work claims scored:**

- Formerly KittyCAD, org still `kittycad` — **CONFIRMED**.
- Products = Design Studio, Zookeeper, KCL, API at api.zoo.dev with OpenAPI + bearer auth
  covering ML/Modeling/File — **CONFIRMED** (spec fetched and enumerated below).
- "Engine returns B-rep, not meshes" — **CONFIRMED**. zoo.dev/text-to-cad: Text-to-CAD
  "generates B-Rep surfaces … you can import a STEP file from Text-to-CAD into any existing
  CAD program and edit it." The API spec adds: *"our source of truth for the resulting
  model is a STEP file."*
- SOC 2 Type II — **CONFIRMED** (https://zoo.dev/blog/soc2, report at trust.zoo.dev).
- "ITAR compliance" — **CORRECTED**: what exists is an ITAR-suitable **"US Regulated
  region"** offering ("suitable for processing or storing export restricted (ITAR)
  information, operated out of US-based cloud providers that meet or exceed ITAR
  baselines"). The standard ToS contains only a generic export-compliance clause; blanket
  "Zoo is ITAR compliant" is too strong. Default cloud ≠ ITAR environment.
- Open question "is any of it self-hostable" — **ANSWERED: no.** Engine is cloud-only.
- "Wrap, not replace, build123d" — endorsed; this plan does exactly that.

### The API surface (from the fetched OpenAPI spec)

Auth: bearer API token (`Authorization: Bearer $ZOO_API_TOKEN`), created per-user at
zoo.dev/account or via `POST /user/api-tokens`; orgs get `POST /org/service-accounts`.
The spec declares no `securitySchemes` block; the bearer scheme is per the docs and all
four SDKs. **No OAuth required anywhere for API use** (an OAuth2 device-grant + PKCE flow
exists in the API, but it is optional — see §Zookeeper below). Rate limits: **not declared
in the spec and not published — UNVERIFIED**; the practical limiter is the credit balance,
and "No Charge for Failed Calls" (zoo.dev/api-pricing).

- **ML / generation** (`ml` tag):
  - `POST /ai/text-to-cad/{output_format}?kcl=true` — the classic generate endpoint.
    **Async**: returns 201 with an `id`; poll `GET /async/operations/{id}` or
    `GET /user/text-to-cad/{id}`. Status enum: `queued|uploaded|in_progress|completed|failed`.
    Response carries `code` (the KCL source, "will be required … once we are at v1"),
    `outputs` (map of file-path → base64 file in the requested format), `error`,
    `conversation_id`. Cache hits return immediately. The spec's own description says:
    *"Prefer the ML copilot websocket (`/ws/ml/copilot`) for new integrations"* — the REST
    endpoint is maintained-but-legacy.
  - `POST /ml/text-to-cad/iteration` (edit existing KCL: `original_source_code` +
    `source_ranges` required) and `POST /ml/text-to-cad/multi-file/iteration`
    (multi-file projects, multi-turn via `conversation_id`) — the AI edit loop.
  - `POST /ml/kcl/completions` (beta), `POST /ml/convert/proprietary-to-kcl` (hidden),
    `GET /ml/conversations`, custom-models + org-datasets endpoints (enterprise RAG-ish).
- **WebSockets**: `GET /ws/ml/copilot` (the conversational agent channel),
  `GET /ws/ml/reasoning/{id}` (reasoning stream), `GET /ws/modeling/commands` (raw engine
  proxy — modeling commands in, responses/video frames out; params include
  `video_res_width/height`, `fps`, `webrtc`).
- **File ops** (`file` tag): `POST /file/conversion/{src_format}/{output_format}` — sync
  with base64 `output` if input < 25 MB, else async via the same operations poll. Plus
  `center-of-mass`, `mass`, `density`, `volume`, `surface-area` analysis endpoints.
- Utility: unit conversions, projects/share-links, payments/balance introspection
  (`GET /user/payment/balance` — lets Harvis show remaining credits).

## 2. The export answer (the user's decisive question)

**Formats out** (`FileExportFormat` enum, verified from the spec): **STEP, STL, OBJ, PLY,
glTF, GLB, FBX.** Not supported: IGES, 3MF, DXF, and no KCL-in-the-enum — but KCL source
comes back separately as the `code` field (`?kcl=true` on generation).

**Formats in** (`FileImportFormat`): STEP, STL, OBJ, PLY, glTF, FBX **plus proprietary:
SolidWorks (sldprt), Parasolid, ACIS, CATIA, Creo, Inventor, Siemens NX.** The conversion
endpoint alone is a sleeper feature (SolidWorks → STEP with no local kernel).

**Is it truly editable?** Yes, on two levels — and the distinction matters:

1. **The KCL source is the real parametric artifact.** It is a program: named parameters,
   unit-typed literals (`length = 2mm`), calculations (`length = totalHeight * 0.3`). Edit
   a number, re-execute, get a new model. This is what "fully editable" means in Zoo's
   marketing, and it is genuine — but re-execution requires Zoo's cloud engine.
2. **The STEP export is true analytic B-rep, not a baked mesh.** Verified twice: the API
   spec states STEP is the *source of truth* for every generation, and zoo.dev/text-to-cad
   states it generates "B-Rep surfaces" (exact curves, "not approximations") importable and
   editable "in any existing CAD program." Honest caveat: STEP carries geometry, **not the
   feature tree or parameters** — that is inherent to STEP, not a Zoo limitation. FreeCAD /
   SolidWorks / build123d can modify the solid; the parametric intent lives only in the KCL.

**Billing of export:** the format you request at generation time (plus STEP, always) comes
back in the same call — no separate export charge. Additional conversions of existing
files go through `/file/conversion`, billed as normal API compute seconds.

**So the user's flow — "AI creates the model, then we export it" — is exactly what the API
does in one round-trip:** prompt in → KCL + STEP (+ GLB for the viewer) out.

## 3. What problem it solves for Harvis, and how it composes with build123d

Forge-fab's locked stance: image-first 3D generation yields concept assets, NOT testable
geometry. Zoo is the first adapter that crosses that line: **prompt → real B-rep solid +
editable parametric source.** It fills the "AI drafts the part" slot that build123d (a
deterministic kernel, not a generator) intentionally does not fill.

Composition (wrap, not replace):

- **Zoo = generation lane.** Prompt/iteration produces `part.kcl` + `part.step` + `part.glb`.
- **build123d = verification + local lane.** OCCT reads STEP, so every Zoo part can be
  re-imported locally for mass/volume/bounding/section checks and the Stage-1 closed-form
  stress gates. Zoo generates; Harvis verifies locally; nothing engineering-shaped is
  claimed on Zoo's word alone.
- **Viewer**: GLB output drops straight into the existing three.js path (Stage-0 mock viewer,
  `front_end/owui/src/lib/agent-studio/adaptive/HelmetHangerMockViewer.svelte`) via
  GLTFLoader — a frontend-only change.
- **KCL vs build123d authoring split** (the interesting question): let the AI author
  **KCL when the user opts into the cloud lane** (Zoo's ML natively emits KCL, and the
  iteration endpoints edit it surgically via source ranges), and **build123d Python when
  local/offline/deterministic** (our LLMs write Python fine; runs in the executor with zero
  egress). Store both artifact types in the same workspace; STEP is the neutral bridge
  between them. Do not attempt local KCL execution — the toolchain parses locally but
  geometry needs their engine.
- **Boundary with blueprint.io** (sibling research): Zoo owns *geometry* (generate, iterate,
  convert, export). Blueprint.io owns wiring diagrams / BOM / build steps. The only touchpoint
  is "BOM from assembly," which is future work for either — no duplication today.

## 4. Verdict

**WRAP (adopt as the flag-gated lane-5 cloud CAD adapter for forge-fab).** It is the only
service found that turns a prompt into genuinely editable parametric CAD (KCL) plus true
B-rep STEP through a plain bearer-token API, and the adapter costs Harvis ~0 MB. It must
stay an opt-in side lane because the engine is unavoidably cloud-proprietary — a hard cloud
dependency that a local-first product can offer but never require.

## 5. Integration plan (phased)

**Credential handling (all phases):** per-user Zoo API token entered in Settings → API Keys,
stored encrypted following the existing `user_api_keys` / `user_engine_auth` pattern
(`python_back_end/owui_compat/engine_auth.py`, `moonshot_api.py` precedent). The
`model_proxy` invariant holds: the token never reaches the browser and **never enters the
no-egress OpenClaw pod** (its NetworkPolicy already forbids the egress anyway). BYO-key is
also a ToS requirement, not just hygiene — see §8.

**Flag gate (all phases):** new per-capability lane-5 flag `HARVIS_ZOO_ENABLED`
(default OFF), added beside `HARVIS_SSH_ENABLED` / `HARVIS_MCP_RUNTIME_ENABLED` in
`_lane_flag_enabled()` in `python_back_end/workspace/orchestration/authz.py`. Every Zoo
call goes through `authorize_action(lane=5, tool_name="zoo_text_to_cad" …)`.

**Phase 1 — generate + export (the user's ask).**
- New package `python_back_end/zoo_cad/` (files < 500 lines each):
  - `adapter.py` — plain-`httpx` async client (deliberately NOT the `kittycad` SDK, which
    drags pymongo + phonenumbers + pydantic-extra-types for nothing we need).
    `POST /ai/text-to-cad/glb?kcl=true`, poll `GET /user/text-to-cad/{id}` with backoff,
    honor `queued/in_progress/completed/failed`.
  - `router.py` — FastAPI routes `/api/zoo/generate`, `/api/zoo/status/{id}`,
    `/api/zoo/export/{id}` behind JWT + authorize_action; wire into `main.py`,
    proxied by nginx like every `/api/*` route.
- Artifacts land as **lane-2 workspace files**: `part.kcl`, `part.step`, `part.glb`,
  `provenance.json` (prompt, Zoo id, model_version, timestamps, `verified: false`).
- Frontend: a "Generate (Zoo cloud)" action in Adaptive Space; GLB into the existing
  three.js viewer; a download row exposing STEP/KCL/GLB. Show
  `GET /user/payment/balance` so users see remaining credits.
- **First-use consent dialog** (Web-Research-button pattern): states data leaves the
  machine and that Zoo's free tier trains on submissions with no opt-out.

**Phase 2 — iterate.** `POST /ml/text-to-cad/multi-file/iteration` with `conversation_id`
threading; edit loop over the stored KCL in Adaptive Space. Same flag, same lane.

**Phase 3 — local verification bridge (composes with forge-fab Stage 1).** Re-import
`part.step` into build123d in the executor container; compute mass/volume/bbox; run the
closed-form stress gates. Only after this does `provenance.json.verified` flip.

**Phase 4 (optional, later).** `/ws/ml/copilot` conversational lane (Zoo's own recommended
integration path) and `/file/conversion` for user-uploaded proprietary files
(SolidWorks/Creo/NX → STEP). Zoo also ships an MIT MCP server (`github.com/KittyCAD/mcp`)
— once the MCP runtime lane is on, that's a zero-code alternative surface, but the native
adapter should remain the product path (typed artifacts, honesty gates, provenance).

**Honesty gates / failure modes (Phase 1 requirements, not afterthoughts):**
- Every generated part is labeled **"AI-generated — unverified"** until Phase-3 checks run;
  the forge-fab engineering-claim rules apply unchanged (SF < 2.5 → recommend FEA;
  SF < 2.0 → "looks safe" language forbidden). Zoo's output NEVER bypasses these gates.
- `status: failed` or missing `outputs` → surface Zoo's `error` string verbatim; never
  render a stale/placeholder model as if it were the result.
- **Export completeness check**: assert STEP is present in `outputs` before reporting
  success (the spec promises it; verify anyway).
- 401/403 → "Zoo key invalid — re-enter in Settings → API Keys" (mirror the Moonshot
  verify-on-save flow). Timeout/unreachable → "Zoo cloud unreachable; local build123d lane
  still available." Poll cap (e.g. 10 min) → mark failed, keep the Zoo id for later refetch.
- Geometry that exports but is not manufacturable is exactly why Phase 3 exists: Harvis
  states measured facts (mass, volume, SF from closed-form) and otherwise says "not
  verified" — never "Zoo said it's production-ready."

## 7. Distro notes

- **Linux + compose**: backend dials out HTTPS/WSS to api.zoo.dev:443 directly (nginx not
  in the path for egress). No new service, no new ports.
- **Kubernetes**: NetworkPolicy must allow backend egress 443 to api.zoo.dev. **Known trap
  on the current cluster: the campus network blocks outbound UDP/53, so api.zoo.dev won't resolve
  from pods** — same class of fix as `registry.ollama.ai` (CoreDNS hosts entry per
  `K8S_DNS_WORKAROUND.md`), and Zoo is behind a CDN so pin-by-IP is fragile; expect to
  refresh entries. OpenClaw's namespace egress rules must NOT be widened.
- **Windows Harvis (Docker Desktop/WSL2)**: backend runs in Linux containers — identical.
  The viewer path is browser-side three.js/WebGL rendering a small GLB: no server GPU, no
  WSL2 GPU passthrough, no difference on Windows. (Only if Harvis ever embedded Zoo's live
  `/ws/modeling` engine stream would WebRTC/video enter the picture — also browser-side,
  but skip it; static GLB is the right integration.)

## 8. Risks, license, ToS, export-control traps

- **Hard cloud dependency** (the big one): no self-host, ever, for the engine. If Zoo
  changes pricing/API or dies, the lane dies — mitigated because it's a side adapter and
  every artifact (KCL + STEP) is stored locally and STEP remains usable offline.
- **ToS resale clause**: "You will not … frame, mirror, sell, resell, rent or lease Use of
  the Services" (zoo.dev/terms-and-conditions). A shared Harvis-operated key serving many
  users would plausibly violate this. **BYO-key per user is mandatory**, which is our
  pattern anyway.
- **Training on user data**: Zoo gets a broad license to "Customer Materials" including
  model training; opt-out exists **only on paid tiers** — the pricing API literally lists
  Free as "Zoo can train on your data (no opt out)". Harvis must disclose this in the
  consent dialog; prompts may contain proprietary design intent.
- **IP of outputs**: "Subject to Section 7(b), you own and retain all right, title and
  interest (if any) in the Outputs." No non-commercial restriction was found in the
  extracted clauses — but **read §7(b) in full before shipping**; the "(if any)" hedge and
  the section cross-reference were not fully retrievable in this pass. UNVERIFIED detail.
- **Export control**: standard cloud is NOT an ITAR environment; ToS puts export-law
  compliance on the user. A Harvis user handling ITAR data must not send it through the
  default adapter (Zoo's "US Regulated region" is an enterprise arrangement). Worth one
  sentence in the consent dialog.
- **API drift**: spec is v0.1.0; the REST text-to-cad endpoint is already
  "kept for existing clients" with the copilot websocket preferred — plan Phase 4
  accordingly and pin response parsing defensively.
- **Rate limits unpublished** — treat 429s as a first-class failure mode. UNVERIFIED.
- Verify before trusting: (a) actual STEP quality on a nontrivial prompt round-tripped
  through build123d (analytic surfaces vs tessellated NURBS soup), (b) real seconds-per-
  generation for cost, (c) §7(b) text, (d) whether `?kcl=true` reliably returns `code`
  today. All four are one afternoon with a free account ($10 credits).
